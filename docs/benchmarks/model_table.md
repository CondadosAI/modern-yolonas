# Model table: accuracy, size and latency

Generated by `examples/model_table.py`. Every column is measured here rather than quoted,
so the table can be regenerated and any disagreement is reproducible:

```bash
uv run examples/model_table.py --coco ~/datasets/coco --half --nms-iou 0.70
```

## Protocol

- **Weights**: the pretrained COCO checkpoints this library downloads, which originate
  from Deci's super-gradients releases. Not weights trained by this project.
- **Accuracy**: full COCO val2017, all 5000 images, `pycocotools`. Input letterboxed to
  640 with aspect preserved; NMS at confidence 0.001 and IoU 0.70 (see the sweep below).
  Predictions are mapped
  back to original image coordinates before being compared with the ground truth.
- **Parameters**: `sum(p.numel() for p in model.parameters())`.
- **FLOPs**: `torch.utils.flop_counter` for one 640×640 forward pass, multiplies and adds
  counted separately. Papers that report a "GFLOPs" figure roughly half of these are
  counting multiply-accumulates instead; compare conventions before comparing numbers.
- **Latency**: PyTorch FP16 on an RTX 3060 Laptop, batch 1, model forward only — no
  preprocessing, no NMS — median of 30 runs after 8 warmup runs, synchronous single
  stream. See [the latency matrix](latency_matrix.md) for other runtimes, devices and
  precisions; TensorRT on the same GPU is roughly an order of magnitude faster than the
  PyTorch figure here.

## On comparing this with published leaderboards

Detection leaderboards usually report latency on an NVIDIA T4 with TensorRT at batch 1.
That is not the hardware above, and a latency number is meaningless without its protocol,
so the two columns should not be read side by side. The accuracy columns are directly
comparable — they are the standard COCO val2017 metrics.

## How this compares with Deci's published figures

Deci publishes 47.5 / 51.5 / 52.2 for S / M / L; this table measures 47.3 / 51.3 / 52.0 on
the same weights — 0.2 under, for each of the three. The residual is small and, so far, unexplained —
what follows is what was tested rather than what sounds plausible.

Four probes on YOLO-NAS-S over full val2017, changing one thing at a time:

| protocol change | mAP |
|---|---:|
| centred letterbox padding, NMS IoU 0.65 | 47.20 |
| centred padding, **NMS IoU 0.70** | **47.32** |
| centred padding, NMS IoU 0.80 | 47.20 |
| bottom-right padding, NMS IoU 0.65 | 47.00 |
| NMS IoU 0.65, crowd annotations stripped from the ground truth | 46.77 |

What each one settles:

- **Padding convention.** super-gradients pads bottom-right rather than centred, so it was
  worth checking whether this repo's centred padding costs accuracy. It does not — centred
  measures 0.2 *better*. Ruled out.
- **NMS IoU.** 0.70 is the local optimum; 0.65 and 0.80 are both worse. This table is
  measured at 0.70. Note that `postprocess` still defaults to 0.65, which is the better
  operating point for interactive use, where fewer overlapping boxes matters more than the
  last tenth of AP.
- **`iscrowd`.** Stripping crowd annotations from the ground truth *lowers* AP by 0.43,
  which shows the evaluation already handles them correctly: `COCOEvaluator` scores against
  the annotation file, and `pycocotools` marks crowd regions ignore rather than background,
  so a detection firing inside one is not punished. This is worth stating because
  `data/coco.py` does drop crowd annotations — but those targets feed the training loss,
  never this number.

That leaves **roughly 0.2 unaccounted for**, the same for all three variants. Pinning it down would need Deci's
own evaluation code to compare interpolation, resize and precision choices against; no
guess is offered here.

Numeric agreement with super-gradients is verified separately and far more tightly — class
scores are bit-identical. See [the parity report](parity.md). Whatever the residual is, it
is in the evaluation protocol and not in the network.
